01 / The complete decision loop

There is no single planner class. Goal selection, periodic motives, reactive opportunities, and activity states cooperate through persistent guest fields. Arrows below show conceptual dependencies, not a single strict function-call order.

Current engine: motives to outcomes
100%

Native needs and thoughts remain simulation data. The generated Qwen sentence does not command a guest.

Two update rhythms

PeepUpdateAll() calls every guest's update() each tick. Periodic work is staggered by guest iteration index every 128 ticks; much of the heavier motive logic runs every 512 ticks, and some need/thought work every 1,024. Activity execution is also gated by movement step progress.

Feedback is the real character state

Rides affect satisfaction, nausea, favorites, and ride history. Purchases affect cash and inventory. Food, rest, queues, and surroundings change motives. Future decisions consume that state; a generated sentence is not the source of truth.

02 / Choosing what to do

These are separate rule paths, not one globally optimized utility function. The ordinary ride picker favors excitement; facility targeting favors geometric proximity; leaving and local behavior have their own conditions.

Current engine: independent goal-setting routes
100%

A map expands candidate knowledge. It does not make paths reachable, reserve a place in a queue, or guarantee the best walking distance.

Do not treat willingness checks as pure queries. shouldGoOnRide(..., thinking=true) can still reset headings and modify ride flags. A model's candidate builder needs read-only eligibility logic, not repeated side-effectful probes from a worker.

03 / Finding the next step

The engine turns a persistent goal into one next direction. A bounded depth-first heuristic search explores the connected path layout; it is neither a full optimal route planner nor a model decision.

Current engine: tile-to-tile navigation
100%

This is a conceptual compression of branching code. Outside-park navigation, wide paths, signs, slopes, queue ownership, and local edge pruning affect the actual route.

Bounded exploration

15,000 tile checks for guests, divided across candidate directions. A search branch stops at 200 steps. Normal guests get five thin junctions of lookahead; a map or departure can increase that to seven, and some lost departing guests get eight.

Small navigation memory

The last four thin junctions retain untried directions. Revisited junctions can explore alternatives. A new or invalidated goal resets history; this is not a stored end-to-end route.

Three different destinations

guestHeadingToRideId: high-level intent. pathfindGoal: navigation goal. destinationX/Y: immediate walking point. Setting only coordinates does not create a persistent ride goal.

04 / Acting in the world

A goal does not bypass an activity's rules. Queue membership, vehicle boarding, shop transactions, and local object occupancy belong to native state machines. This diagram groups detailed ride substates into readable stages.

05 / A small decision model, not a second simulator PROPOSED

Use D3-Lite (0.8B) or D3-Edge (0.6B) to choose among supplied valid actions. The full D3 model is outside this experiment's intended GPU budget. Official model cards describe typed choice, yes/no, and score outputs without text generation; see model sources.

Scope boundary: controller candidates only. Neither model has been integrated or benchmarked on this Windows ARM64 / CUDA machine. Existing llama.cpp support for Qwen guest narration does not establish runtime compatibility, GPU fit, or throughput for these decision models.
Proposed: asynchronous, bounded goal selection
100%

Suggested first deployment: shadow mode. Observe decisions alongside native behavior before allowing any simulation changes.

What the model may choose

A small hierarchical choice: first the activity or need, then a supplied target. Example IDs below are illustrative, not live park data.

{
  "choices": [
    "continue_current_goal",
    "visit_food_shop_17",
    "visit_gentle_ride_42",
    "visit_toilets_9",
    "wander"
  ]
}

A goal is a typed request, not permission to invent a ride ID or execute arbitrary engine code.

What stays native

  • Tile movement, signs, slopes, queue spacing, seats, and vehicle interaction.
  • Admission, accounting, inventory, and actual motive changes.
  • Critical recovery behavior: picked guests, falling, drowning, invalid paths.
  • Local bench/bin handling until explicit destination support is designed.
  • Fallback when inference is missing, late, invalid, or low confidence.
Simulation changes are not display changes. Do not let an inference worker write to guest entities. Start with single-player or shadow mode. Multiplayer and replay support require synchronized, recorded decisions and a controlled application tick; even deterministic inference can diverge if completion timing differs.

GPU budget

Benchmark controller + selected narrator + game together. Keep small models resident if feasible, batch work, bound request frequency, and measure real latency and memory rather than extrapolating from parameter counts.

Behavior budget

Not every guest needs a decision every tick. Use goal completion and significant state changes, preserve current intent, impose cooldowns, and reject stale results to prevent oscillation and wasted work.

Evidence before control

Shadow-log native choice, model choice, candidates, state, confidence, and latency. An unexecuted model choice has no measured outcome: use controlled A/B simulations for causal behavior comparisons.
